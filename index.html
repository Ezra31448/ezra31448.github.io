01 / The short version

Good QA is less about finding more bugs. It’s about finding the right ones early.

I like to get close to the workflow: what a person is trying to do, what the system should remember, and where a small mismatch can become a big issue.

Make the expected behavior obvious. Make the evidence useful.

My work sits between product intent and what the software actually does. I test the happy path, then stay around for the messy path: empty fields, duplicate data, strange files, broken links, and everything that only appears after a change.

03 / How I work

Understand → challenge → prove → repeat.

When code is produced with an AI coding assistant, I treat the output like any other implementation: run it, question it, verify it, and leave a clear trail for the next person.

01

Understand

Read the task, ask what success looks like, and map the real user flow.

02

Challenge

Test the edges: bad input, odd files, permissions, empty states, and data that repeats.

03

Prove

Report what happened with steps, evidence, expected behavior, and a clear priority.

04

Repeat

Verify the fix, run the regression sweep, and check that the change did not move the problem elsewhere.
